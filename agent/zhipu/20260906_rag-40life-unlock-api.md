---

## 1. 需求背景与目标

**现状**：`40-Life` 目录位于 RAG 基线规则（basePatterns）中，与 `.mimocode` / `node_modules` / `.obsidian` 一样**永久排除**，任何会话都无法检索。

**新需求**：`40-Life` 要能被检索，但必须**先提供密钥解锁**——即把它从「硬排除」升级为「**默认不可见、密钥授权后限时可见**」的隐私保护区。

**设计目标**：

1. 默认行为完全不变（不解锁 = 和现在一样检索不到）
2. 解锁以**会话为维度**、**限时自动失效**，而不是全局永久放开
3. 密钥本身不落库、不进前端存储，只在解锁请求中传输一次
4. 回答是否用了 40-Life 内容，前端可感知（打专属标签）

---

## 2. 前端交互设计（后端据此理解契约形态）

前端计划这样消费这组接口，后端实现时请保证以下体验可成立：

```
输入舱工具区：  [📄 知识库检索] [🔒 40-Life]        ← 新增锁形胶囊
                      │ 点击
                      ▼
        弹出密钥输入框 → POST /api/rag/life/unlock
                      │ 成功
                      ▼
        胶囊变为 [🔓 40-Life · 剩余28分]（倒计时）
        此会话提问可命中 40-Life，回答气泡追加 🔒 标签
```

- 密钥**只在解锁请求里传输一次**，前端不持久化（不进 localStorage）
- 解锁状态倒计时结束 / 用户主动上锁 / 清空记忆 → 胶囊回到 🔒
- 设置卡片中 `40-Life` 基线 chip 将显示为「🔒 可解锁」样式，状态区展示锁定的文件/分块规模（见 3.5）

## 3. 接口契约（期望后端按此实现）

### 3.1 POST /api/rag/life/unlock —— 解锁

请求体：

```json
{ "conversationId": "web:475a2830-...", "key": "用户输入的密钥" }
```

成功 `200`：

```json
{ "unlocked": true, "expiresAt": "2026-09-06T15:30:00", "remainingSeconds": 1800 }
```

失败：

| 状态码 | 场景 | 响应体（纯文本，前端直接展示） |
| --- | --- | --- |
| `400` | conversationId 缺失 / key 为空 | `参数不完整` |
| `401` | 密钥错误 | `密钥不正确` |
| `429` | 短时间失败过多（防爆破） | `尝试次数过多，请 10 分钟后再试` |

> 失败用纯文本 + 非 200，与 `/api/rag/patterns` 的 400 风格保持一致，前端统一按「非 2xx → 读 text() 展示」处理。

### 3.2 POST /api/rag/life/lock —— 主动上锁（可选但希望有）

```json
{ "conversationId": "web:475a2830-..." }
```

成功 `200`：`{ "locked": true }`。用户点胶囊「立即上锁」时调用；404 / 无解锁态也返回 200 即可（幂等）。

### 3.3 GET /api/rag/life/status?conversationId=... —— 查询解锁态

```json
{ "unlocked": true, "expiresAt": "2026-09-06T15:30:00", "remainingSeconds": 1234 }
```

前端在页面加载、切换会话、每次打开胶囊菜单时轮询/按需查询，用于恢复锁形胶囊状态。未解锁返回 `{ "unlocked": false }`（200，不要用 404 区分）。

### 3.4 POST /api/reply —— 行为变化

- 请求体**不变**（仍传 `useRag` / `sessionId`，不传密钥——解锁态由后端按 conversationId 判定）
- 行为变化：该会话处于解锁态且 `useRag=true` 时，检索范围**包含 40-Life**
- **响应体新增字段 `lifeUsed`**：

```jsonc
{ "reply": "...", "ragUsed": true, "provider": "zhipu", "lifeUsed": true }
```

- `lifeUsed: true` 仅表示本次检索命中了 40-Life 的内容，前端将渲染 🔒 专属标签
- `message_log.use_rag` 落库行为不变；是否需要单独标记 lifeUsed 见第 7 节待确认项

### 3.5 GET /api/rag/status —— 响应扩展

```jsonc
{
  "enabled": true, "vaultPath": "...", "files": 24, "chunks": 79, "lastError": "",
  "lifeFiles": 3,        // 新增：40-Life 被锁定保护的文件数
  "lifeChunks": 12       // 新增：40-Life 被锁定保护的分块数
}
```

前端设置卡片用它显示「🔒 40-Life：3 文件 · 12 块（解锁后可检索）」。

### 3.6 GET /api/rag/search —— 调试接口扩展（可选）

增加可选参数 `conversationId`：传入且该会话已解锁时，检索结果包含 40-Life 命中；不传保持现状（排除）。方便前端「试一试」功能与主链路行为一致。

## 4. 解锁状态管理（后端实现要点建议）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 存储 | **内存** `Map<conversationId, expireAt>` | 重启即失效 = 天然安全兜底；隐私授权态没有落库必要 |
| 时效 | 默认 **30 分钟**，可配置；上限建议 ≤ 24h | 「限时可见」是需求核心，过期必须自动收紧 |
| 防爆破 | 按会话 + 按 IP 双维度计数：连续失败 5 次 → 429 锁 10 分钟 | 密钥是唯一门槛，必须防暴力枚举 |
| 密钥存储 | 环境变量（如 `RAG_LIFE_KEY`），**禁止写入任何提交的配置文件**；比较用常量时间比较 | 与 `ZHIPU_API_KEY` 同一管理约定 |
| 与清空记忆的关系 | 「清空记忆」指令处理时**顺带移除解锁态** | 语义一致：忘掉上下文 = 收回隐私授权 |
| 多会话隔离 | 解锁只对发起解锁的 conversationId 生效，不影响其他会话 | 最小授权原则 |

> 备选方案（已否决）：每条 `/api/reply` 直接带 `lifeKey` 字段。更"无状态"但用户体验极差（每个问题都要输密钥），且密钥会频繁出现在请求流水里。

---

## 5. 检索层实现建议

推荐 **「单索引 + 检索时过滤」**，而非双索引：

- 索引构建时照常把 40-Life 一起建进索引（现状不变）
- 检索执行时：会话未解锁 → 在检索层按 chunk 的来源路径元数据**过滤掉 40-Life 命中**；已解锁 → 不过滤
- 理由：避免维护两份索引的内存与重建开销；过滤发生在检索层，与现有隐私边界声明一致（不动 message_log / 对话记忆）
- 注意：`/api/rag/search` 不带 conversationId 时必须保持现状（过滤 40-Life），避免调试接口变成绕过入口

## 6. 前端联调自测清单（后端实现后按此验收）

- [ ] 未解锁时提问「我 40-Life 里的 xxx」→ 回复不命中、`lifeUsed` 缺省/false
- [ ] 错误密钥 unlock → 401 + 文本「密钥不正确」，前端正常展示
- [ ] 正确密钥 unlock → 200 + expiresAt；同会话再问 → 命中且 `lifeUsed: true`
- [ ] 换一个 conversationId 用相同密钥 → 需要重新解锁（隔离性）
- [ ] 到期后（可临时把 TTL 配成 1 分钟）→ 再问不命中，`GET life/status` 返回 unlocked:false
- [ ] 连错 5 次 → 第 6 次返回 429
- [ ] 「清空记忆」后 → 解锁态消失
- [ ] `/api/rag/status` 能看到 `lifeFiles` / `lifeChunks` 且数字合理
- [ ] 后端重启 → 所有解锁态自动失效
